## Plan: Full repo review & improvements

TL;DR: Improve error handling & exit code clarity, logging, cross-platform support (Windows), testing coverage for edge cases (network & async), and minor code cleanup. Address high-risk bugs and propose safe refactors (including optional async migration).

### Summary of High-Level Findings
- main.rs is clean and minimal; `try_main()` is a good separation point for tests. However, error handling and exit-code semantics could be made clearer and more actionable for users and CI.
- Project uses blocking code (reqwest blocking), D-Bus for some actions; both are platform-sensitive. Ensure cross-platform detection and graceful fallbacks.
- Tests are extensive but more unit tests can be added around `try_main()` and `Config::load()` error fallback behavior, and more explicit tests around CLI subcommands and their exit codes.
- `anyhow` is used, but internal module errors could benefit from typed error enums (`thiserror`) for easier control and assertions.
- Several style/efficiency improvements: reduce unnecessary `clone()`, remove inefficient matches, unify log formatting, add consistent contextual logging (`anyhow::Context`), and inject test-friendly behaviors (dependency injection for clients).
- Consider optional future async conversion with `tokio`/async reqwest for better scalability in longer-running daemon mode.

### 1) Exit-code & Error Handling: Add richer semantics (High severity) ✅
- Problem: `main()` maps any `try_main()` error to `ExitCode::from(1)`, losing context and making different error categories indistinguishable (config error vs network failure vs action failure).
- Why it matters: More precise exit codes help automation, integration tests, and better UX in scripts that use `check_vpn`.
- Fix:
  - Introduce small `enum ExitReason { Success, ConfigError, RuntimeError, ActionFailed, ArgsError }` and a function `exit_code_for_error(E) -> ExitCode`.
  - Convert `anyhow` errors to typed error kinds at boundaries (validate, map `app::run` errors to a custom enum).
  - Update `main()` to map these error cases to distinct exit codes (e.g., 1 = generic, 2 = config, 3 = action failed).
- Files to change:
  - main.rs (map errors to different `ExitCode`)
  - Introduce `src/errors.rs` or `src/error_types.rs` with typed `enum` (or `thiserror`).
  - Update `app::run`, `config::load`, and action runner errors to propagate typed errors or convert to `ExitReason`.
- Tests:
  - Add tests for different `try_main` error paths (simulate config file missing vs invalid vs runtime network error).
  - Acceptance: `cargo test` must include at least one test checking the exit code mapping.

### 2) Logging: More robust contextual & trace-level logging (High severity / Medium impact) ⚠️
- Problem: logger is initialized in `try_main()` with `args.verbose`. Some errors are logged only with `error!("...: {}", e)` and omit context or backtrace unless `RUST_BACKTRACE` is set manually.
- Why it matters: Better logs help troubleshooting and provide clearer, actionable messages for ops.
- Fix:
  - Use `anyhow::Context` (or `map_err(|e| e.context("..."))`) to add context to errors when appropriate.
  - Log with `log::error!("{:?}", e)` or leverage `anyhow` to print full error chain when verbose.
  - Add `panic::set_hook` to log panics if appropriate and unify formatting for timestamps/levels (already in logging crate?).
  - Consider switch to `tracing` for structured logs if future features need observability; otherwise add structured key-value fields in log contexts.
  - Clarify logging initialization behavior, e.g., ensure `init_with_verbosity` covers default log levels and `RUST_LOG` precedence.
- Files:
  - logging.rs (enhance defaults & docs)
  - main.rs, add richer logging around `config::load` fallback
  - `src/app/*` and critical functions to add `Context` messages for `?` calls.
- Tests:
  - Add unit tests ensuring log output includes critical context for certain error paths. (Or use `log-test` crate to capture logs.)

### 3) Config loading: Explicit errors / validation vs silent fallback (Medium severity) 💡
- Problem: `Config::load()` errors are logged and the program falls back to default; this is desirable in resilient systems, but may hide config mistakes.
- Why it matters: Running with defaults after a corrupted or malformed config may be undesirable for users who expect strict behavior.
- Fix:
  - Add a CLI flag `--strict-config` or `--fail-on-config-error` that returns a non-zero exit code for `Config::load` errors to catch user config mistakes.
  - Add more granular log message with suggestions and include the config path.
  - Consider returning `Result<Config, ConfigError>` with typed `ConfigError`, and map to a distinct exit code.
- Files:
  - mod.rs, validation.rs
  - mod.rs for a new flag
- Tests:
  - Add tests to simulate `Config::load()` parse error and verify default-fallback behavior vs `--strict-config` returns non-zero.

- Fix:

  - Add clear log messages when an action is skipped due to platform limitations.
- Files:
